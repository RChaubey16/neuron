## Code conventions

Every method in a `*.service.ts` file must have a JSDoc block directly above it describing what it does, any exceptions it throws, and (when non-trivial) the reasoning behind non-obvious steps. Follow this shape:

```typescript
/**
 * Creates a new user record.
 * Throws a ConflictException if a user with the same email already exists.
 *
 * @param createUserDto - Validated payload from the incoming request
 * @returns The newly created user entity
 */
async create(createUserDto: CreateUserDto): Promise<User> {
  const existing = await this.userRepository.findOne({
    where: { email: createUserDto.email },
  });

  if (existing) {
    throw new ConflictException('A user with this email already exists');
  }

  // Repository.create() only builds the entity instance in memory,
  // it does not persist it — save() is what hits the DB
  const user = this.userRepository.create(createUserDto);
  return this.userRepository.save(user);
}
```

- The JSDoc block goes above the method signature: a one-to-two sentence summary, a line for each exception the method can throw, then `@param`/`@returns` tags for anything not self-evident from the type signature.
- Inline `//` comments inside the method body are still reserved for non-obvious behavior (e.g. a framework quirk like `create()` vs `save()` above) — don't restate what the code already says.
- This applies to every method on a service class, including trivial ones — keep the JSDoc proportional (a one-line summary is fine for a one-line method).
- Controllers return response DTOs (`class-transformer`'s `@Expose()`), never Prisma entities directly — see `src/auth/dto/user-response.dto.ts`. `main.ts` registers a global `ClassSerializerInterceptor` and `ValidationPipe({ whitelist: true, forbidNonWhitelisted: true })`; new request-body DTOs should use `class-validator` decorators to get validation for free.

## Prisma / Nest gotchas specific to this repo

- **Prisma client generator must stay `prisma-client-js`, not the newer `prisma-client`.** The new generator emits `.ts` files with no `index` entrypoint and relies on ESM-style relative imports (`./enums.js` etc.) that break under this project's CommonJS ts-jest setup. `prisma-client-js` outputs a classic CJS `index.js` and just works.
- **Prisma 7 requires an explicit driver adapter** — `PrismaClient` no longer auto-reads `DATABASE_URL`. `PrismaService` passes `new PrismaPg({ connectionString: process.env.DATABASE_URL })` explicitly; don't remove that when touching `src/prisma/prisma.service.ts`.
- **`@prisma/client-runtime-utils` must stay a direct dependency**, not just a transitive one pulled in by `@prisma/client`. `pnpm prune --prod` (used in the Dockerfile's build stage) drops it otherwise, likely because `@prisma/client` lists `prisma` as an optional peer dependency and that confuses pnpm's prune graph — this breaks the runtime image with `Cannot find module '@prisma/client-runtime-utils'` even though local `pnpm run build`/tests pass fine.
- **`@nestjs/config` must stay pinned to the 4.x line, not 12.x.** The 12.x release is ESM-only and fails Jest's CommonJS runner immediately on import.
- **Session JWTs are self-signed by this app, not Supabase.** `AuthService.signToken` uses `@nestjs/jwt`'s `JwtService.signAsync`, keyed by `JWT_SECRET`; `JwtAuthGuard` verifies with the same secret. `GOOGLE_CALLBACK_URL` must exactly match the redirect URI registered on the Google Cloud OAuth client, or the OAuth handshake fails before it ever reaches this app. `jose` and Supabase's JWKS endpoint are no longer used anywhere in the codebase.
- **`@nestjs/jwt` and `@nestjs/passport` must stay pinned to the 11.x line, not 12.x.** Same class of problem as the old `jose` 6.x/`@nestjs/config` 12.x/`nanoid` 4.x traps: 12.x ships `"type": "module"` with no CJS build and breaks Jest's CommonJS runner immediately on import. 11.x has no `"type"` field (defaults to CommonJS) and loads cleanly under ts-jest. This wasn't caught by a first "does it resolve" check based on `tsc`/`nest build` alone — that check passed even against the ESM-only 12.x line because of the worktree-nesting issue below; only an actual `pnpm run test` run (or a build from a properly isolated location) surfaces the real ESM failure.
- **A git worktree nested inside this repo (e.g. under `.claude/worktrees/...`) can silently resolve a removed dependency from the *outer* repo's `node_modules`, masking a real "module not found" error.** Node/TypeScript module resolution walks up parent directories looking for `node_modules`, and a worktree living inside the main repo's directory tree eventually reaches the main repo's own `node_modules` if the worktree's own copy doesn't have the package. This produced a false-negative `pnpm run build` pass in this worktree after `jose` was removed from `package.json` (Task 2 of the Google OAuth migration) — the outer repo (on `main`) still had `jose` installed, and TypeScript quietly resolved the import through it instead of erroring. `docker build --target build` (a genuinely isolated filesystem) is the reliable way to confirm a dependency is actually gone; don't trust a worktree-local `pnpm run build`/`nest build` for that specific question.
- **`JwtModule` must be re-exported from `AuthModule`, not just imported.** `JwtService` (unlike `ConfigService`/`PrismaService`) isn't a global provider, so `JwtAuthGuard` — used via `@UseGuards(JwtAuthGuard)` in `ApiKeyModule`/`UsageModule`, which only `imports: [AuthModule]` — couldn't resolve its own `JwtService` dependency without this. Nest resolves a guard class referenced by `@UseGuards()` from across the whole DI graph (see the guard/interceptor gotcha below), but that guard's *own* constructor dependencies still resolve from whatever module scope it's actually registered in — they aren't automatically visible just because a consuming module imports the module that provides the guard.
- **`ConfigService.get<T>(key)` returns `T | undefined`, not `T`, even for env vars `env.validation.ts` guarantees are present.** Passing that into a third-party library type expecting a required non-optional field (e.g. passport-google-oauth20's `StrategyOptions.clientID: string`) produces a confusing TypeScript overload-resolution error that doesn't obviously point at the real cause (in `GoogleStrategy`, it manifested as "missing `passReqToCallback`" on an unrelated overload). Use `configService.getOrThrow<T>(key)` for any required config value — it's safe here specifically because startup validation already guarantees the value exists.
- **`AuthService.findOrCreateUser`'s upsert must key on `email`, not `id`.** `User.id` holds whatever the current auth provider's stable identifier is (Google's `sub`, previously a Supabase-issued UUID), but `User.email` is the column with the actual `@unique` constraint. Upserting on `id` means a pre-existing row under a different `id` (e.g. any user who logged in before this Supabase→Google migration) doesn't match the lookup and falls through to `create`, which then crashes with a `PrismaClientKnownRequestError` (`P2002` on `User_email_key`) instead of linking to the existing account. Confirmed by reproducing the crash during Task 10 manual verification against a real leftover Phase 2 test row, then fixing it and re-verifying.
- **A parameter typed with an interface that has no runtime representation (e.g. Express's `Response`) inside a method using both a param decorator and `emitDecoratorMetadata` needs a type-only import.** `@Res() res: Response` failed `nest build` with `TS1272` under this project's `isolatedModules` + `emitDecoratorMetadata` config until `Response` was split into its own `import type { Response } from 'express'` (separate from the regular `import { Request } from 'express'`, since `Request` is only ever used inside an intersection type here and didn't trigger the same error).
- **`prisma7.config.ts` (repo root) and the `prisma/` directory must both stay excluded from `tsconfig.build.json`.** If TypeScript includes either (e.g. `prisma/seed.ts`) in `nest build`, the inferred `rootDir` widens to the repo root and the compiled entrypoint becomes `dist/src/main.js` instead of `dist/main.js` — breaking not just `start:prod`/Docker's `CMD ["node", "dist/main"]`, but also `nest start --watch`: it compiles cleanly and logs "Watching for file changes" but then hangs forever with zero further output, because it tries to launch the app from the entry path it expects and that path doesn't exist. No error is printed — it just looks stuck. This exact regression happened when `prisma/seed.ts` was added in Phase 1 without adding `prisma` to the exclude list.
- **Corepack pins the package manager version from `package.json`'s `packageManager` field** — the Docker build copies `package.json` before running any `pnpm` command specifically so Corepack fetches the same pnpm version as local dev. Without that pin, Corepack grabs the latest pnpm, which (as of pnpm 11) enables a `minimumReleaseAge` supply-chain check by default that rejects any dependency published within roughly the last day — this silently breaks `pnpm install --frozen-lockfile` in CI/Docker whenever a transitive dependency had a same-day release.
- **The seed command is wired via `prisma7.config.ts`'s `migrations.seed`** (`"ts-node prisma/seed.ts"`), not the legacy `package.json` `"prisma": { "seed": ... }` field — Prisma 7's config-based setup doesn't read that field. Run it with `pnpm exec prisma db seed`.
- **`prisma init` scaffolds AI-agent "skill" reference docs** (`.claude/`, `.windsurf/`, `.agents/`, `skills-lock.json`) at the repo root as a side effect. These aren't project files — delete them if `prisma init` is ever re-run.
- **A Prisma query builder call (e.g. `prisma.apiKey.update(...)`) returns a lazy "PrismaPromise" that only executes once something calls `.then()`/`.catch()` on it (or awaits it)** — unlike a native `Promise`, whose executor runs eagerly regardless of subscription. `void prisma.apiKey.update(...)` for a fire-and-forget write (e.g. `ApiKeyGuard`'s non-blocking `lastUsedAt` update, `UsageLoggingInterceptor`'s `UsageLog` write, `ShortUrlService.resolve`'s `clickCount` increment) silently never sends the query: no error, no log, the row just never changes. The fix is `.catch(() => {})` (or `.then()`), not `void` — this actually subscribes, triggering execution while still not blocking the caller. Confirmed by reproducing the silent-no-op against the real Supabase DB, and by unit tests that mock a lazy thenable (a real `Promise` mock can't catch this, since it'd execute regardless of subscription) — this is now a standard regression test on every fire-and-forget write in the codebase.
- **`nanoid` must stay pinned to the 3.x line, not 4.x/latest.** Same class of problem as `jose`/`@nestjs/config`/`prisma-client`: nanoid 4+ (confirmed on 6.0.1) ships ESM-only (`"type": "module"`, no CJS entrypoint) and breaks Jest's CommonJS runner on import. nanoid 3.x (e.g. `3.3.8`) still ships a `"main": "index.cjs"` alongside its ESM `"module"` entry, so `require('nanoid')` resolves correctly under ts-jest.
- **`ShortUrlModule` must stay the last import in `AppModule`, and `GET /:code` must stay the last route registered.** NestJS/Express match routes in registration order, not by specificity — a single-segment catch-all param route like `GET /:code` registered before another top-level `GET` route (e.g. `/health`, `/usage`) would silently shadow it, since routing doesn't prefer the more specific static path. `test/short-url.e2e-spec.ts` has a standing regression test asserting `GET /health` still resolves correctly with the shortener module wired in.
- **A guard/interceptor referenced by class (`@UseGuards(ApiKeyGuard)`, `@UseInterceptors(UsageLoggingInterceptor)`) resolves across the *entire* app's DI graph, not just the providers visible to the controller's own module.** This is why `test/api-keys.e2e-spec.ts` and `test/short-url.e2e-spec.ts` could apply `ApiKeyGuard` to a controller declared directly on the root testing module and have it work, with no explicit import anywhere in that test. Real feature modules still import the module that provides a guard they use (e.g. `ShortUrlModule` imports `ApiKeyModule`) — not because Nest requires it to resolve, but because the import is the only place that dependency is documented; without it, the guard's presence is invisible from reading the module file.
- **`process.env` is now validated at startup** via `validate` in `src/config/env.validation.ts`, wired into `ConfigModule.forRoot({ validate })` in `app.module.ts` — required: `DATABASE_URL`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `GOOGLE_CALLBACK_URL` (well-formed URL), `JWT_SECRET`, `FRONTEND_URL` (well-formed URL); `JWT_EXPIRES_IN` and `PORT` are optional. A missing/malformed value now fails fast with a clear `Invalid environment configuration: ...` error instead of a confusing downstream crash. Any test that compiles `AppModule` (i.e. every e2e spec) runs this validation against the real process environment even though `PrismaService`/`JwtService`/`GoogleStrategy` are mocked — CI (`.github/workflows/ci.yml`) supplies hardcoded-but-well-formed dummy values for exactly this reason, and a local `.env` (gitignored, not inherited by a git worktree) needs the same set to run `pnpm run test:e2e` outside CI. `env.validation.ts` needs its own `import 'reflect-metadata'` since it's the first place in this codebase that runs `class-validator` decorator-based validation (`validateSync`) outside of a full Nest bootstrap, which is what normally loads that polyfill as a side effect.
- **`@typescript-eslint/no-unused-vars` is configured with `ignoreRestSiblings: true`** in `eslint.config.mjs` specifically for the "destructure to omit a key" test pattern (e.g. `const { DATABASE_URL: _omit, ...rest } = validEnv;` in `env.validation.spec.ts`) — without it, the extracted-but-unused sibling fails lint even though the whole point is to discard it. Unused function *parameters* prefixed with `_` (e.g. `GoogleStrategy.validate`'s `_accessToken`) are already ignored by typescript-eslint's defaults; this option is specifically for unused *variables* from destructuring, which aren't covered by that default.

## Project overview

**Neuron** is a single NestJS + Supabase (Postgres via Prisma) platform exposing shared backend services (notifications, URL shortener, and future services) behind one unified API.

- **Humans** authenticate via self-hosted Google OAuth (Nest-issued session JWTs) to a dashboard for managing API keys.
- **Machines** (other apps) call service endpoints using an API key via the `x-api-key` header.
- Every authenticated service call is recorded in a `UsageLog` for analytics/debugging.

## Architecture (planned)

- **Auth model is dual-track**: dashboard routes are protected by a `JwtAuthGuard` (verifies the Nest-issued session JWT for logged-in humans, signed via `@nestjs/jwt`); service routes are protected by an `ApiKeyGuard` (hashes the incoming `x-api-key`, looks up a match, rejects if missing/revoked). Don't conflate the two — a dashboard session token and a service API key are different credentials with different guards.
- **API keys are hashed at rest** — only `crypto.randomBytes`-generated raw keys are returned once at creation; the stored record keeps only the hash plus a `keyPrefix` for display. Never persist or log the raw key.
- **Usage logging is cross-cutting, not per-service**: a `UsageLoggingInterceptor` (or logic inside `ApiKeyGuard`) writes a `UsageLog` row (`apiKeyId`, `service`, `endpoint`, timestamp) automatically for every authenticated request, async/non-blocking, so individual service modules don't implement logging themselves.
- **Each service is an isolated NestJS module** following the same `Module + Controller + Service + ApiKeyGuard` pattern (see Notifications and URL Shortener as the first two, Phase 9 lists future services). New services should replicate this shape rather than introducing a new pattern.
- **Supabase is database-only** (Postgres via Prisma for `User`/`ApiKey`/`UsageLog`/service tables) — it no longer handles auth. Google OAuth (`passport-google-oauth20`) plus Nest-issued session JWTs (`@nestjs/jwt`) handle human login instead. A `User` row is lazily created on a user's first Google login (`AuthService.findOrCreateUser`, keyed by Google's `sub` claim), so app-level user records don't exist until then.
- **Async work runs through a queue** (BullMQ + Redis, or a Supabase-based queue) — e.g. notification sending — so request handlers return fast and failures are retried rather than surfaced synchronously.
- **The public-facing exception is the redirect route**: `GET /:code` for the URL shortener is intentionally unauthenticated (meant to be hit directly by browsers), unlike every other service route.
- Target deployment is a single multi-stage Docker image (deps → build → slim runtime) built starting in Phase 0 and reused unmodified through Phase 8 deployment — avoid introducing a second build path later.

## Build order dependencies

Phases 0–4 (setup → data model → dashboard auth → API keys → usage logging) are strictly sequential and form the shared infrastructure every service depends on. Phases 5 (Notifications) and 6 (URL Shortener) only depend on Phase 4 being done — they don't depend on each other and can be built in parallel or in either order. Phase 7 (hardening) and Phase 8 (deployment) come last.
